# Agent Guide

## Project Goal

This repository is The Table Church's website: a plain Astro site serving `thetabletx.org`.

The repository is the source of truth. Routes live in `src/pages/`, navigation in
`src/config/navigation.ts`, shared facts in `src/config/site.ts`, and the visual system in
`design.md`. Read those rather than any external site.

The goal is an Astro site that:

- follows the design system in `design.md` — the cream/slate print-poster system built from the church's own printed and social graphics
- stays small enough that a single maintainer can hold the whole thing in their head
- serves its media from this repository rather than hotlinking it elsewhere
- documents intentional external dependencies such as Church Center, social links, YouTube embeds, events, and form flows

Current work is verification and content accuracy, not schema expansion.

## Repository Shape

The app lives at the repository root.

```text
design.md               The locked visual system — read before writing any markup or CSS
ROADMAP.md              Planned work and known gaps
astro.config.mjs        Astro config (server output, Node standalone adapter)
src/pages/              One .astro file per public route
src/layouts/            Layout.astro (shell) and ContentPage.astro (inner pages)
src/components/         SiteHeader, SiteFooter, ContentSidebar
src/config/             site.ts (shared facts), navigation.ts (menu), domains.mjs (canonical host)
src/content/            Markdown collections: series/ and messages/
src/content.config.ts   Zod schemas for those two collections
src/lib/                content, mailer, podcast, rate-limit, sermon-chatbot
src/styles/             tokens.css (design tokens), global.css, content-page.css
public/                 Static files served as-is
scripts/                Node/tsx tooling: transcript ingest, media automation, server start, smoke test
data/transcripts/       Sermon transcripts (VTT + generated markdown) used by /ask
docs/                   Reference docs, including external-resources.md
```

## Content Model

Deliberately minimal. Two kinds of content, two different editing paths:

**Static pages** — `src/pages/*.astro`. Page copy lives in the component. There is no `pages` collection, no `[...slug].astro`, and no CMS. Editing a page means editing its `.astro` file. This is intentional: the pages change rarely, and a markdown-per-page indirection layer costs more than it returns.

**Series and messages** — `src/content/series/*.md` and `src/content/messages/*.md`, validated by `src/content.config.ts`. These are the collections that carry real recurring data (sermon archive, podcast feed) and they are partly machine-generated by the ingest scripts. Routes: `/series/` and `/series/[slug]/`.

Rules for the collections:

- flat frontmatter, clear field names (`title`, `description`, `speaker`, `draft`)
- omit optional fields entirely rather than leaving them blank
- `draft: true` until content is ready; every route filters with `!data.draft`
- filename-derived slugs unless a custom `slug` is genuinely needed
- a published message must reference a series (enforced by the schema)

Shared facts — address, service time, podcast links, social links — live in `src/config/site.ts`. Menu structure lives in `src/config/navigation.ts`. Change those, not the individual pages.

## Media

- `public/attachments/` — media referenced by pages and series. Served at `/attachments/...`. Frontmatter may use the `attachments/...` form; `resolveAsset()` in `src/lib/content.ts` prefixes it.
- `public/images/scrapbook/` — curated, web-sized photography (long edge 1600px, EXIF stripped). Committed.
- `public/attachments/scrapbook/` — full-resolution originals from the photographer. **Git-ignored.** Never commit these; they run ~700MB. Pull a candidate through the resize step into `public/images/scrapbook/` instead.

Keep committed media web-sized. Full-resolution originals and raw video belong outside git.

## Build And Verification

Run everything from the repository root.

```bash
npm run dev -- --host 127.0.0.1   # dev server
npm run build                     # production build
npm start                         # serve the build (scripts/start.mjs)
npm test                          # unit tests for scripts/ and src/
npm run test:smoke                # boot the build, crawl every route (needs a build first)
```

CI (`.github/workflows/verify.yml`) runs test, build, and smoke on every push and PR.

A green build only proves the site compiles. After content, route, or layout changes, open the affected routes in a browser and check them against `design.md`. If the dev server serves a stale 404 for a page that builds, restart it.

## Deployment

Render, using `render.yaml`: `npm ci && npm run build`, then `HOST=0.0.0.0 npm start`. Secrets (SMTP, LLM keys, analytics IDs) are set in the Render dashboard, not committed. Render is the only deployment target.

## External Dependencies

The church's own material also lives outside this repository — Google Workspace, the
YouTube channel, Church Center. What is where, which account the connectors can
actually reach, and what a session may do with it is in
[`docs/external-resources.md`](docs/external-resources.md).

These destinations are intentionally external. Do not convert them into broken local routes:

- Giving / Church Center
- social links
- YouTube embeds
- Church Center MeetUp interest forms
- future events and form integrations unless explicitly built into the site

## Planning Gate

Use a strict progression for new ideas and proposed changes:

1. **Roadmap first** — new ideas and future work belong in `ROADMAP.md`. Do not turn brainstorming directly into repo changes.
2. **Implementation second** — do not change code, docs, scripts, or config for a new idea without a roadmap entry or an explicit request. If reality shows the work is partly done, update `ROADMAP.md` and leave the remainder as its own entry.

Work the roadmap one item at a time: confirm the item is still valid against current code, explain what you intend to change and why, then pause for approval before implementing.

If the user is discussing ideas, stay in planning mode. Move to implementation only when the work has clearly crossed the gate.

## Agent Operating Principle

Two constraints, both binding:

1. The visual system in `design.md` governs. It is a print-poster system, not a web-app system — cards, pills, drop shadows, and rounded corners are foreign to it. Extend or amend `design.md` when the system needs to grow; do not invent a per-page look beside it.
2. The codebase should stay lean — a plain Astro site with an obvious folder structure, no content-management layer that only one person understands.

If those conflict, make the tradeoff explicit before adding complexity. Do not introduce a CMS or other content-management abstraction without an explicit decision.
